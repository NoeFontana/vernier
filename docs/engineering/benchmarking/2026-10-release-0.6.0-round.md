# 2026-10 release round — the 0.6.0 numbers

Full release-mode re-measurement ahead of tagging `v0.6.0`, at
`a79f67e6ba7e` on host `a6ada888c850`, the same fingerprint as the 0.5.5
round, so round-over-round deltas are direct. Every published cell comes
from this one result tree, rendered into [`docs/benchmarks.md`](../../benchmarks.md).

New in this round: **`ultrafast-pycocotools==0.1.14` (ufcoco)** is a
baseline on every instance cell, every thread-scaling column and
Objects365 (PR #374). Other baselines unchanged: `hotcoco==1.0.1`,
`faster-coco-eval==1.8.0`, `pycocotools==2.0.11`, `boundary-iou-api@37d2558`,
`panopticapi@7bb4655`, `mmsegmentation@c685fe6`, `lvis-api@031ac21`.

What 0.6.0 changes is the instance core: Structure-of-Arrays detections
with columnar ingest and a packed category-major evaluation grid
(ADR-0066), the true-positive accumulate sweep (ADR-0068), work-balanced
parallel evaluation, parallel JSON splitting and field-skipping parse,
plus faster RLE decoding and polygon rasterization. `vernier-panoptic` and
`vernier-semantic` are untouched, which makes their cells the control.

0.5.5 → 0.6.0, vernier: Nano bbox 954.6 → 492.5 ms (−48 %), Seg-Nano bbox
1.288 → 0.576 s (−55 %), Seg-Nano segm 2.343 → 1.431 s (−39 %). hotcoco
moved +1.8 %, +0.1 % and +1.0 % on the same cells, so the host is steady.

Peak RSS on Nano bbox: vernier 257 MiB (390 MiB in 0.5.5), ufcoco 225 MiB,
hotcoco 997 MiB, faster-coco-eval 1.35 GiB, pycocotools 1.40 GiB.

**Where ufcoco stands.** It is the closest competitor, and the margin is
ingest, not matching. On Nano bbox vernier's stages are load 56 ms (GT
only — vernier parses the detections inside `evaluate`), evaluate 375 ms,
accumulate 60 ms; ufcoco's are load 285 ms, evaluate 251 ms (its
accumulate is folded in), accumulate ~0. ufcoco's single-thread matching
kernel is the faster one; vernier wins on parsing the results file and on
everything multi-threaded.

## Inside a training loop — RF-DETR's own `compute()`

The file-based cells above time JSON loading through each library's own
entry point. RF-DETR evaluates differently: its `OnePassCocoMeanAveragePrecision`
accumulates detections as tensors and hands them to the backend at the end of
the epoch, unthresholded (`num_select` queries per image) at
`max_detection_thresholds=[1, 10, 500]`. To measure that path, the metric
state was captured from `RFDETRNano` / `RFDETRSegNano` `.evaluate(split="val")`
on rf-detr `develop` @ `bc7385e` and `compute()` was replayed per backend, one
fresh process per run, arms rotated, 7 rounds (`eval_backend="vernier"` at this
SHA vs `eval_backend="ufcoco"`, 0.1.14).

- det: Nano, all 5,000 val2017 images × 300 queries = 1.5M detections, `bbox`.
- seg: Seg-Nano, the first 1,000 val2017 images by id × 100 queries, `bbox` + `segm`.

Default threading (what a training run gets: no caps, no pinning). "warm" is a
second `compute()` in the same process, the epoch-2+ case:

| workload | vernier cold / warm | ufcoco cold / warm | ratio cold / warm |
| --- | ---: | ---: | ---: |
| det | **0.333 / 0.283 s** | 0.868 / 0.548 s | 2.61× / 1.94× |
| seg | **0.256 / 0.237 s** | 1.369 / 1.087 s | 5.35× / 4.59× |

Equal CPU budget (taskset + `OMP_NUM_THREADS` / `RAYON_NUM_THREADS`), cold:
det 0.426 vs 1.054 s at two CPUs (2.47×) and 0.382 vs 0.960 s at four (2.51×);
seg 0.362 vs 1.572 s (4.34×) and 0.304 vs 1.490 s (4.90×). Metrics were
identical across arms (det `map` 0.48418, seg `segm_map` 0.42899). vernier's
det `compute()` adds 270 MiB at peak against ufcoco's 217 MiB; on seg it adds
96 MiB against 230 MiB.

The in-loop gap is wider than the file-based one. The workloads differ in
ways the file cells do not exercise — 3× the detections (unthresholded
queries), `maxDets=500`, and the two adapters' ingest: rf-detr builds
pycocotools-shaped ground-truth records for ufcoco, while vernier ingests
the stored columns directly (`coco_inputs_from_columns` → `DetectionsBatch`).
How much each contributes was not separately measured.
